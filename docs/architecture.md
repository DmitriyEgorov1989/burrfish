# Архитектурные правила Burrfish

## Стиль решения

Burrfish разрабатывается как модульный монолит на основе Clean Architecture, Domain-Driven Design и CQRS. Один процесс ASP.NET Core содержит HTTP endpoints и фоновые обработчики, но исходный код разделён на проекты с однонаправленными зависимостями.

## Проекты и зависимости

Разрешённый граф зависимостей:

```text
Burrfish.Api ──────────────> Burrfish.Application
      │                              │
      └────> Burrfish.Infrastructure │
                     │               │
                     ├───────────────┘
                     └──────────────> Burrfish.Domain

Burrfish.Application ───────────────> Burrfish.Domain
Burrfish.Domain ─────────────────────> нет проектных зависимостей
```

- `Burrfish.Domain` содержит предметную модель, инварианты, агрегаты, сущности, value objects, доменные события и ожидаемые доменные результаты. Проект не зависит от MediatR, EF Core, ASP.NET Core, конфигурации или внешних API.
- `Burrfish.Application` содержит команды, запросы, MediatR handlers, прикладные сценарии и порты, которые нужны этим сценариям. Проект зависит только от `Burrfish.Domain` и MediatR.
- `Burrfish.Infrastructure` содержит EF Core, PostgreSQL, inbox/outbox, фоновые обработчики и адаптеры Meta, OpenAI и Telegram. Проект реализует порты `Burrfish.Application` и может зависеть от `Burrfish.Application` и `Burrfish.Domain`.
- `Burrfish.Api` является composition root: принимает HTTP-запросы, связывает зависимости, регистрирует hosted workers и преобразует HTTP-контракты в команды или запросы. Бизнес-правила в `Burrfish.Api` запрещены.
- Обратные зависимости, циклические ссылки и прямые ссылки `Domain` или `Application` на `Infrastructure` и `Api` запрещены.

## Domain-Driven Design

- Использовать единый предметный язык из спецификации: `Conversation`, `Lead`, `Intent`, `Handoff` и `OperatorHandoff`.
- Инварианты защищаются внутри агрегата. Публичные setters и изменение состояния в MediatR handler запрещены.
- Первый aggregate root — `Conversation`; границы других агрегатов добавляются только при появлении собственного инварианта и транзакционной границы.
- `Lead` создаётся только через подтверждённый переход `Conversation` в `OperatorHandoff`.
- Value object применяется, когда значение имеет собственную проверку или семантику. Обёртки без поведения не создаются.
- Ожидаемые доменные ошибки возвращаются как типизированный result и не используются для управления потоком через исключения.
- Доменные события описываются собственными типами Domain. Зависимость Domain от `INotification` MediatR запрещена; публикация адаптируется в Application.
- Абстрактные `Entity`, `AggregateRoot` и generic repository не создаются заранее. Общий примитив вводится только после появления минимум двух подтверждённых применений.

## CQRS и MediatR

- Команда изменяет состояние и называется глаголом в повелительной форме, например `ProcessIncomingMessageCommand`.
- Запрос не изменяет состояние и возвращает read model, а не aggregate root.
- Каждая команда или запрос имеет один handler в `Burrfish.Application`.
- HTTP endpoint и background worker вызывают сценарий через `ISender`; прямой вызов handler запрещён.
- MediatR не является шиной интеграционных событий и не заменяет PostgreSQL inbox/outbox.
- Транзакция охватывает один прикладной сценарий изменения состояния. Внешние вызовы выполняются через outbox после фиксации транзакции.
- Pipeline behaviors добавляются только для сквозной политики с несколькими реальными потребителями. Пустые logging, validation или transaction behaviors заранее не создаются.
- Используется `MediatR 12.5.0` с лицензией Apache-2.0. Переход на версию с другой лицензией требует отдельного согласования.

## Порты и адаптеры

- Порт объявляется в `Burrfish.Application`, если прикладной сценарий должен заменить внешний механизм в тесте или production.
- Адаптер порта находится в `Burrfish.Infrastructure`.
- Интерфейс должен скрывать детали внешнего API и возвращать исходный код и сообщение ожидаемой интеграционной ошибки без утечки чувствительных данных.
- Generic repository запрещён. Репозиторий выражает операции конкретного агрегата или прикладного сценария.

## Тестовые границы

- `Burrfish.Domain.Tests` проверяет инварианты агрегатов без MediatR, базы данных и mocks инфраструктуры.
- `Burrfish.Application.Tests` проверяет commands, queries и handlers через их публичные интерфейсы с тестовыми адаптерами портов.
- `Burrfish.Infrastructure.Tests` проверяет persistence и адаптеры; PostgreSQL-тесты используют Testcontainers и требуют Docker.
- `Burrfish.ApiContract.Tests` проверяет публичные HTTP-контракты и преобразование запросов в CQRS messages.
- Сквозные тесты проверяют один пользовательский сценарий через публичный endpoint и реальные внутренние границы с подменой только внешних API.

## Правила изменений

- Новое бизнес-правило сначала формулируется как инвариант Domain или прикладное правило Application.
- Новый внешний API сначала получает порт Application и только затем адаптер Infrastructure.
- Новый endpoint не получает прямой доступ к `DbContext`, repository или внешнему HTTP client.
- Изменение графа зависимостей проектов требует обновления этого документа и предварительного согласования.
